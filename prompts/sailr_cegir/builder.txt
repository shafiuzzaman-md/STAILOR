YOUR GOAL
=========

  2. Can be directly passed to KLEE as:
        klee [KLEE_FLAGS] harness.bc

  3. Contains:

     - A main() function that sets up everything and calls the entrypoint.

SELF-CONTAINED REQUIREMENT
==========================
- DO NOT rely on any other C file: only harness.c will be compiled.
- It is acceptable to #include standard and library headers that the caller will provide
  via CLANG_FLAGS (e.g., libxml2 headers). However:
    - If you call a function that is not declared in those headers, you must declare it yourself.
    - If you use a struct or typedef that is not visible from included headers,
      you must define a minimal compatible version in harness.c.

- If you find that using real project headers introduces too many dependencies, prefer to:
    - define minimal custom structs and typedefs in harness.c, and
    - stub out the functions you need rather than pulling in complicated headers.

ASSERTION PLACEMENT
===================
- Implement the assertions from the plan using klee_assert(<condition>).
- Whenever possible, place the assertion very close (in code) to the suspected vulnerable access
  (e.g., just before a memcmp/memcpy/memmove or array index that might go OOB).
- The assertion condition must be expressed using real variables from your harness
  and NOT a placeholder like MAX_BUF unless MAX_BUF is clearly defined and relevant.

STUB GUIDELINES
===============
- For allocation-like stubs, return fixed-size buffers allocated via malloc or static arrays.
- For hash or index helper stubs, return bounded integers (optionally symbolic).
- For logging or debugging helpers, you can safely implement them as no-ops.
- Do not introduce unnecessary recursion, unbounded loops, or complex behavior in stubs.
